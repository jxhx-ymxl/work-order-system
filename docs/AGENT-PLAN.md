## 2. [复核修正] 需要修正的七处

| # | 问题 | 上一版的不足 | 修正 |
| --- | --- | --- | --- |
| 1 | **agent 的价值可能被高估** | 报告被限制为事实编号和模板建议后，很多结果可以直接由规则产生 | 增加三组对照：**纯规则报告 → 固定查询＋LLM → agent**；避免只证明 agent 优于一个本来就不需要模型的方案（详见 §7） |

## 3. [复核修正] 完成判据与终止协议

### 3.1 [已定稿 2026-10-05] "调查完成"的可执行定义

- **首版（S1）只声明三类问题 + 一类兜底**，且都是**协议演示用虚构类型**（理由见 §1 收口结论第 1 条）：

| 问题类型 | 必需事实（必须被引用证据覆盖） | 允许未知项（未知也计"已覆盖"，但报告须显式标未知） | 建议前提（不满足则不得给该类建议） |
| --- | --- | --- | --- |

| `REASSIGN_HISTORY` 被谁处理过 / 转过几手 | `order.exists`、`order.accept_events` | 无（`accept_events` 为空数组是**完整事实**，不是未知） | `accept_events` 为空时**不得建议"联系处理人"（`suggestionIds` 不得含 `CONTACT_ASSIGNEE`，禁止项）**；建议方向是"等待指派 / 主管介入"——**方向是提示，不是强制项** |
| `UNSUPPORTED` 不属于上述三类 | 无 | — | 证据与建议都必须是**空数组**；只允许输出"不属于首版支持范围"，不得给出事实性结论 |

- **完成与否由后端校验事实覆盖度决定，不由模型自报**：校验规则 = 报告声明的 `problemType` 的每个必需事实，
  都能被报告引用的证据编号覆盖；任何一个覆盖不到 → 报告判为**未完成**（走 §3.2 的重试 / 失败路径）。
- **判据落在证据的 `fact` 字段上，不落在模型的说法上**：模型写十句"已确认状态为处理中"却没引用 `order.status` 的证据，仍判未覆盖。
- **"允许未知项"是后端强制的，不只是提示**：被引用的证据若带未知标记，而该事实不在该类型的"允许未知项"里，
  报告同样判未完成——那等于把"不知道"写成结论。落地在 `InvestigationAgent.validateReport`，

- **"标未知"在 S1 落在证据上**（`AgentEvidence.unknown=true`），报告正文渲染在 S2；报告本身仍只有编号。
- **条件必需事实（D82 裁决，2026-10-06）**：当证据能证明 `order.exists=false` 时，该类型的必需事实**收缩为 `{order.exists}`**——
  "工单不存在"本身就是一个可完成的结论，不该因为拿不到状态 / 处理人而永远判未完成
  （落地在 `InvestigationAgent.validateReport`：按证据的 `fact` + `value` 判定，不新增字段）。
- **空值语义与"未知"分开（D82）**：`order.sla_deadline` 为 NULL 是**已知的"无 SLA 截止"**（只给值、**不标未知**），
  与 `order.accept_events` 为空走 `emptyFacts` 同一口径；`order.alert_count` 无记录源时**才是**未知。
- **"建议前提"分两档（2026-10-06 裁决，见 §11-4）**：
  - **禁止项（要做，S2 随真实工具落地）**：`order.assignee` 未知（未分配）时、或 `order.accept_events` 为空时，
    `suggestionIds` **不得含 `CONTACT_ASSIGNEE`**——不许把"不知道找谁"变成"建议联系某人"。
  - **无原因结论（C1 裁决，2026-10-06）**：`TIMEOUT_SITUATION` **不得输出原因性结论**，

  - **过期判定（要做，S2 随真实工具落地）**：`TIMEOUT_SITUATION` 的"`sla_deadline` 是否已过期"必须实现，

  - **强制项（不做）**：不实现"必须建议 X"——那会把建议变成填空题；表里"建议方向"只是提示。

### 3.2 [已定稿 2026-10-05] `finish_report` 终止动作

- 模型通过 `finish_report` 结束调查，**只提交三个字段**：`problemType`、`evidenceIds`、`suggestionIds`；
  报告正文由后端按证据渲染。**模型不提交自由文本结论**——否则"模型自述"就成了唯一依据。
- **它不是第五个业务查询工具**：
  - 不注册进工具表（`AgentToolRegistry`），模型无法"查询"它；
  - 预算口径**单独计** `reportSubmissions`，上限 **2**（首次 + 一次重试），**不占**工具调用预算（§3.4）。
    理由：混在一起会让"查了几次"和"交了几次报告"互相抢占额度，而终止动作的代价与一次业务查询完全不同。
- **校验项（全部由后端做）**：① 每个 `evidenceId` / `suggestionId` 在本轮真实存在；
  ② §3.1 的必需事实全覆盖；③ `UNSUPPORTED` 时两个数组都为空。
- **终止动作必须单独一轮提交**：`finish_report` 与其它工具调用混在同一轮 → `FAILED(MODEL_PROTOCOL_ERROR)`。
  理由：混在一轮会允许"报告引用同一轮才产生、模型还没看到结果的证据编号"——那不是模型的判断，是协议的巧合。
- **校验失败的处理（本条已裁决）**：第 1 次不通过 → 把**缺口清单**（哪些编号不存在 / 哪些必需事实没被覆盖）
  作为系统消息回传，允许重交 1 次；第 2 次仍不通过 → 终态 `FAILED(REPORT_INVALID)`，**不产出报告**。
- **不可绕过**：终态为 `FAILED` / `TIMED_OUT` / `CANCELLED` 的运行，`report` 必须为 `null`——
  这是"失败不得被伪装成正常报告"的机器判据，S1 用测试钉住。

### 3.3 [已定稿 2026-10-05] 对外状态组合

| 状态 | 进入条件 | 终态 | 对外呈现 |
| --- | --- | --- | --- |
| `RUNNING` | 已受理、未出终态 | 否 | 调查中 |
| `COMPLETED` | 报告通过 §3.2 全部校验 | 是 | 报告（`problemType` 可能是 `UNSUPPORTED`） |

| `TIMED_OUT` | 运行预算 60s 到（§4.1）；或模型读取超时 | 是 | 超时 + 原因码，**无报告** |

失败 / 终止原因码（首版全集）：

| 原因码 | 含义 |
| --- | --- |
| `RUN_BUDGET_EXCEEDED` | 运行时间超过 60s |
| `TOOL_BUDGET_EXCEEDED` | 工具调用次数超过上限（§3.4） |
| `ROUND_LIMIT_EXCEEDED` | 模型轮次超过上限（§3.4） |
| `RESPONSE_TOO_LARGE` | 模型响应超过读取上限（§4.2） |

| `MODEL_PROTOCOL_ERROR` | 响应可读但不是合法协议（既无工具调用也无终止动作 / JSON 非法） |
| `REPORT_INVALID` | 报告两次校验均不通过（§3.2） |

| `USER_CANCELLED` | 用户主动取消 |

> 收口时删掉了原先拟的 `NOT_SUPPORTED`：**"不属于支持范围"由 `COMPLETED` + `problemType=UNSUPPORTED` 表达**
> （它是结论，不是故障）；而"模型交出一个不在列表里的类型"属报告非法，走 `REPORT_INVALID`。
> 留一个永远不会产生的状态码，只会让下一个人以为它需要被实现（回读校验时发现，遂删）。

**"永久调查中"的反面**：任何进入 `RUNNING` 的运行都必须同时挂在**三个有上限的口径**上——运行时间（60s）、
工具调用次数（12）、模型轮次（8）。三者任一触顶都进终态，**没有任何路径会停在 `RUNNING`**。

**权限撤销与业务状态变化的终态**：权限撤销 → `CANCELLED(PERMISSION_REVOKED)`；
业务状态变化导致关键证据变化 → `FAILED(STALE_EVIDENCE)`（首版整份作废，不做局部修补，见 §5）。

**S2 的承诺边界（2026-10-06 定稿，D79）**：`ToolContext` 是**受理时的一次性快照**（§11-2），
所以"受理之后"发生的调岗 / 撤权**在执行期间不会被感知**——S2 **只承诺"受理时正确"，不承诺"执行期间实时"**；
"执行期间权限变化"由本条的 `PERMISSION_REVOKED`（S4）覆盖，S1/S2 都不得声称已覆盖它。

⚠ **S1 落地状态**：这两个原因码在 S1 **只登记不落地**——S1 没有权限来源、也没有业务表，无法产生这两类事件；
它们在 S4 由"断开 / 重启 / 权限撤销 / 业务状态变化"四个用例断言。
S1 的测试只覆盖 `RUNNING → COMPLETED / FAILED / TIMED_OUT` 这条主干，**不得声称已覆盖权限与业务状态变化**。

**单轮不得超过剩余预算（2026-10-06 补）**：每次模型调用的读取超时按
`min(剩余运行预算, 模型读取超时)` 收敛，连接超时同样不超过它。理由：只按"每轮上限 30s"算，
轮次上限 8 轮最坏是 240s，与上表的 60s 链条直接矛盾；收敛后整轮的时间上限就是剩余预算（复核发现 4）。

### 4.2 读取阶段的限流与释放

- 限字节必须落在**读取循环里**（读满即中止并释放连接），不能在读完整响应之后再判大小。
- 取消要验到**底层资源真的释放**：用慢响应、超大响应、连接不结束三种桩。
- 取消后**名额要归还**（并发位、连接、线程）。

**S1 已落地的部分与初值**：模型响应体上限 **256KB**（`AgentLimits.maxModelResponseBytes`，在
`HttpAgentModel.readAtMost` 的读取循环里判定），超过即 `FAILED(RESPONSE_TOO_LARGE)`；
"取消要验到资源释放"与"名额归还"属 S4 的异步接口范围，S1 **未落地**。

**取消延迟上界 = 当前轮读超时（2026-10-06 裁决）**：阻塞 `read` **不响应 `interrupt`**，
所以"取消"只会在当前轮的读超时返回之后才生效——**不能把 `Future.cancel(true)` 当成"资源已释放"**。
该上界已被剩余预算收敛（见 §4.1），要缩短只能换可中断 IO，属 S4 选型；S4 验收必须包含
"连接真的断开 + 名额真的归还"的实证，见 §11-3。

① 长度 / 字节数、② 证据与建议编号、③ 截断到 200 字符且**已脱敏**的摘要（沿用 `OrderTriageServiceImpl.brief` 的口径）。

**代价**：脱敏是文本正则而非字段级强隔离，`content` 里非标准写法的个人信息（口语化数字、拼音、昵称）拦不住——

### 11-1 回填给模型的 assistant 消息：字段白名单 —— 采纳，**本片已实施**

  `tool_calls` 内只留 `id` / `type` / `function.name` / `function.arguments`。
- **落地**：模型边界 `HttpAgentModel.assistantMessageForEcho` 做清洗；字段 `ModelTurn.rawMessage` 更名

  assistant 消息，断言第二轮请求里只剩白名单字段），先红后绿见附 D.2。
- **代价**：供应商若靠某个扩展字段维持多轮上下文，会丢。**无证据**（本机没有真 key 复测）；
  真 key 复测时一并验，若真出现丢失，再谈"按供应商扩展白名单"。

### 11-2 工具调用上下文 —— 采纳方向，**形状与授权口径已定稿**，S2 第一片实施

- **裁决**：采纳方向。形状原为"只定形状"，**2026-10-06 补定为**：
  - **签名**：`AgentTool.execute(ToolContext ctx, JsonNode arguments)`；`ctx` 由调查循环构造并传入。
  - **`ToolContext` 的字段（三个，刻意压到最少；2026-10-06 C2 裁决由四个删为三个）**：
    - `investigationId` —— 本次调查的 id（日志与审计的串联键，**不是**用户身份）；
    - `callerUserId` —— 发起调查的用户 id（**唯一**的用户身份来源）；
    - `callerDeptId` —— 发起人所属部门 id；**它是唯一的范围载体**——§1 第二题裁定"统一只查本部门，
      升级状态不扩大可见范围"，因此**不接受任何"可跨部门"标志**（原 `canSeeAllDepts` 字段已删除）。
  - **工具的硬性约束**：`AgentTool` 实现**不得**读 Sa-Token（`StpUtil`）、**不得**依赖
    `RequestContextHolder`、不得读取任何"当前请求"的隐式状态；需要身份就**只用 `ctx` 里的字段**。
  - **授权口径（2026-10-06 定稿，`docs/DECISIONS.md` **D79**）**：
    - **取值时点**：`ToolContext` 在**受理调查的 Web 请求**里**一次性快照、之后不可变**；
      执行侧（S4 的消费 / 调度线程）**不重新取值**——理由同上，那里没有会话，想取也取不到。
    - **判定方**：`callerDeptId` 由**受理层**用与业务接口**同一套**权限判定得出
      （与列表接口的部门过滤同源）；agent 侧**不得**另写 `isAdmin()` / "可见全部" 之类的本地判断
      ——两套判定迟早漂移，而漂移的方向总是"一边放宽"。
    - **拒绝方式**：用**构造期不变量**（`IllegalArgumentException`），**不新开失败码**——
      `ToolContext` 的紧凑构造器拒绝 `null` / 空白 / 缺部门（标识字段首版按**不透明字符串**处理；
      类型属实现细节，S2 可定，但不变量不得放宽）。**造不出对象，就没有"跑到一半才发现越权"的路径。**
    - **硬约束**：**`callerDeptId` 必须非空**（构造期拒绝 `null` / 空白）。§1 之后没有"跨部门"这个口子，
      所以"缺部门"就等价于"没有过滤条件"（= 越权）——**不存在的状态不该能构造出来**。
    - **承诺边界**：S2 **只承诺"受理时正确"，不承诺"执行期间实时"**——快照会过时
      （受理后调岗 / 撤权，本次调查仍按旧权限跑完），这正是 §3.3 的 `PERMISSION_REVOKED`（S4）覆盖的场景。
    - **S2 实施时不得放宽本口径**：放宽 = 改契约，要走 D 条目。
- **排期**：S2 第一片（与第一个真实工具一起改签名）。
- **理由（比"越权风险"更硬的一条）**：S4 的调查跑在**消费 / 调度线程**上，那个线程**没有 Sa-Token 会话**——
  工具若自己去读登录态，不是"可能越权"而是**根本跑不起来**；`RequestContextHolder` 同理（那里没有请求上下文）。
  所以"调用者身份显式传入"不是防御性设计，而是**可行性前提**。
- **代价**：所有工具实现都要改签名（S1 只有 2 个虚构工具，现在是最便宜的时点）；
  `ToolContext` 一旦定下就是**跨片协议**，加字段要走 D 条目——四个字段压到最少正是为此：
  加 `requestId` / `tenantId` 这类"以后可能有用"的字段，就是要避免的过度设计。

### 11-3 取消 —— 采纳，**S4 实施**

- **裁决**：§4.2 补一条**取消延迟上界 = 当前轮读超时**（阻塞 `read` 不响应 `interrupt`，
  所以"取消"只会在读超时返回后才生效）。
- **排期**：S4；验收必须含**连接断开 + 名额归还**的实证（不是"调用过 cancel"）。
- **代价**：用户点了取消之后，最坏仍要等一个读超时（该值已被剩余预算收敛，见 §4.1）；
  要缩短只能把客户端换成可中断 IO，属 S4 的选型。

### 11-4 建议前提分级 —— 采纳，**只做禁止项、不做强制项**

- **裁决边界**：
  - **禁止项（要做）**：`order.assignee` 未知（未分配）时 `suggestionIds` 不得含 `CONTACT_ASSIGNEE`；
    `order.accept_events` 为空时同理不得含 `CONTACT_ASSIGNEE`。
  - **不做强制项**：不实现"必须建议 X"——那会把建议变成填空题。
  - **无原因结论（C1 裁决）**：`TIMEOUT_SITUATION` **不得输出原因性结论**——只交付已核实事实、
    证据缺口与核实建议。约束落在**输出与完成判据**上，名字本身证明不了行为违规。
  - **过期判定（要做）**：`TIMEOUT_SITUATION` 的"`sla_deadline` 是否已过期"必须实现，但**必须用可注入的 `Clock`**，
    不许内联 `Instant.now()`（否则测试不可控、时间源不可替）。
  - **按数据能力对齐的两处（D82，2026-10-06）**：① `order.alert_count` **移出** `TIMEOUT_SITUATION` 的必需事实、
    **保留在允许未知**（映射表已证"无列、只能近似"，不配当必需；若同时从允许未知里删掉，工具返回的显式未知
    一旦被引用就会撞 validateReport 的"该类型不允许未知"分支）；② 证据能证明 `order.exists=false` 时，
    必需事实**收缩为 `{order.exists}`**——"工单不存在"本身就是可完成的结论。两处只改判据口径，不动 §3.1 的其它列。
- **排期**：随 S2 的真实工具（有真实 SLA 数据）落地；S1 保持"仅提示"，§3.1 已标注。
- **代价**：禁止项会拦掉"未分配但确实该联系某人"的场景——首版接受，因为**编造处理人**的代价更高；

### B.3 一条成功轨迹与一条失败轨迹

**成功**（`toolCallThenFinishReport_completes`）：模型请求 `stub_order_snapshot` → 程序执行 →
回传 `{"ok":true,"facts":{...},"evidenceIds":{"order.status":"E2",...}}` →
模型提交 `finish_report{ORDER_STATUS,[E1,E2,E3],[CONTACT_ASSIGNEE]}` → 后端校验三条必需事实全覆盖 →
`COMPLETED`，报告里只有编号。

**失败**（`notAllowedUnknownFact_failsInsteadOfFabricating`）：日志源不可用 → 工具把 `order.accept_events`
标成显式未知 → 模型仍提交 `REASSIGN_HISTORY` 报告 → 后端判未完成（该类型不允许这个事实未知）→
缺口回传 → 模型重交同样内容 → `FAILED(REPORT_INVALID)` 且 `report == null`。
**没有退化成"编一个从未接单的结论"**。

### B.4 为什么失败不会被伪装成正常报告

两条都是机器判据，不靠约定：

1. **构造期不变量**：`AgentRunResult` 的构造器强制"非 `COMPLETED` ⇒ `report == null` 且必须带原因码"。
   任何"失败却又产出报告"的代码路径在构造对象时就抛异常，写不出这种结果。
2. **完成判据落在证据上**：由 §3.1 的必需事实覆盖度判定，不看模型表述；用例
   `modelNarrativeWithoutEvidence_doesNotCount` 专门喂"报告里写结论、一个证据都不引"的输入，验证它仍然失败。
