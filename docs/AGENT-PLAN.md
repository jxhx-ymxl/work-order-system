## 2. [复核修正] 需要修正的七处

| # | 问题 | 上一版的不足 | 修正 |
| --- | --- | --- | --- |
| 1 | **agent 的价值可能被高估** | 报告被限制为事实编号和模板建议后，很多结果可以直接由规则产生 | 增加三组对照：**纯规则报告 → 固定查询＋LLM → agent**；避免只证明 agent 优于一个本来就不需要模型的方案（详见 §7） |
| 2 | **"调查完成"仍不够可执行** | 写了 COMPLETED，却没有说明后端如何判定回答覆盖了问题 | 首版明确支持的问题类型；每类规定必需事实、允许未知项、建议前提；**完成不得由模型自报**（详见 §3.1） |
| 3 | **最终报告协议缺了一环** | 说模型返回结构化草稿，但没有固定它与工具调用协议的关系 | 定义 `finish_report` 终止动作：只提交证据编号和建议编号，由后端验证；它不是第五个业务查询工具，预算口径单列（详见 §3.2） |
| 4 | **新鲜度校验容易误报** | "比较结果指纹"若包含查询时间、耗时、动态超时状态，每次都可能不同 | 只比较稳定业务字段和引用来源；查询时间窗口固定；首版关键证据变化即整份报告标未完成，不做局部修补（详见 §5） |
| 5 | **超时链没有真正对齐** | 设计 60 秒调查，但前端只有 15 秒、Nginx 60 秒 | 调查接口单独配整条超时链，按运行 60 / Servlet 65 / 代理 75 / 前端 80 秒作为待测初值；**不调整所有接口**（详见 §4.1） |
| 6 | **"限大小、能取消"停留在描述** | 读完整响应后再检查大小，无法阻止缓冲占用；Future 结束不代表底层资源释放 | 在**实际读取过程中**限字节；用慢响应、超大响应、连接不结束的桩验证取消与名额释放（详见 §4.2） |
| 7 | **单并发不等于成本控制** | 并发 1 能防积压，却不能防连续重复调用或长期占用 | 启用前补用户频率限制、全局调用预算、忙碌响应；写明进程内计数**重启会丢失**（详见 §4.3） |

外加一条口径修正：**移除"约 20% 改善"的统一门槛**——它缺少业务依据，小样本也支持不了强结论（详见 §7）。

### 2.1 补两项缺口

- **查询成本验证**：`LIMIT 10` 不等于数据库只扫 10 行。相关工单、日志分页、部门关联查询要用代表性数据看执行计划，再决定是否加组合索引。现有索引在 `sql/init.sql:27-31`（`t_work_order` 的 `idx_order_no / idx_status / idx_submitter / idx_assignee / idx_sla`）。**本轮只登记，没有实际测量**。
- **数据外发清单**：不只有工具结果，用户问题本身也可能含手机号、姓名。需规定哪些字段可以发给模型、哪些只留在后端展示，以及错误日志是否泄露原文（详见 §4.4）。

### 2.2 已排除的疑点：测试 profile

`src/test/resources/application.properties` 已默认启用 `test` profile，所以**不能因为测试类没有 `@ActiveProfiles` 就认定它会连业务库**。这条疑点关闭。

仍需补的是：执行前核验实际连接目标，防止环境变量覆盖（`CLAUDE.md` §5「共用外部状态的隔离必须逐项确认」）。

### 2.3 三处独立问题（**不并入本线**）

以下三项仍然成立，但**单独修复、各自提交**，不顺手混进 agent 主功能开发：

1. **清理正则错误**（删前统计谓词）。
2. **信息不足组失败缩分母**（评测口径）。
3. **已有日志授权缺口**。

## 3. [复核修正] 完成判据与终止协议

### 3.1 "调查完成"的可执行定义

- 首版只声明**明确支持的问题类型**，并为每类规定：**必需事实 / 允许未知项 / 建议前提**。
- **完成与否由后端校验事实覆盖度决定，不由模型自报。**
- `[待定]` 首版支持哪些问题类型、每类的必需事实清单——S0 收口时定稿，见 §9。

### 3.2 `finish_report` 终止动作

- 模型通过 `finish_report` 结束调查，**只提交证据编号和建议编号**，由后端校验这些编号是否真实存在、是否覆盖 3.1 的必需事实。
- **它不是第五个业务查询工具**；它的预算口径单独明确（`[待定]`，见 §9）。
- 校验不通过时的处理（重试一次 / 直接判失败）为 `[待定]`。

### 3.3 [待定] 状态组合

对外可见的调查状态机（含"永久调查中"的反面）需在 S0 收口时定稿，至少覆盖：进行中 / 完成 / 失败 / 被取消 / 超时，以及**权限被撤销、业务状态变化**后的终态（对应 §6 的 S4 判据）。

### 3.4 [待定] 预算计数

统一预算的计数对象（工具调用次数 / 模型轮次 / token）、上限值、超限后的终态，S0 收口时定稿。

## 4. [复核修正] 资源与安全边界

### 4.1 超时链（调查接口单独一套，待测初值）

| 层 | 当前值 | 出处 | 调查接口初值 |
| --- | --- | --- | --- |
| 调查运行预算 | — | — | 60s |
| Servlet / 异步 | 未单独配置 | `src/main/resources/application.yml` 的 `server:` 段只有 `port: 9000` | 65s |
| Nginx 代理 | 60s | `deploy/nginx.conf:26`（`proxy_read_timeout`） | 75s |
| 前端 Axios | 15000ms | `frontend/src/utils/request.ts:22` | 80s |

约束：**只给调查接口单独配，不动全局默认值**。四个数字是初值，上线前按 §6 S4 的断开/重启/撤销用例实测校准。

### 4.2 读取阶段的限流与释放

- 限字节必须落在**读取循环里**（读满即中止并释放连接），不能在读完整响应之后再判大小。
- 取消要验到**底层资源真的释放**：用慢响应、超大响应、连接不结束三种桩。
- 取消后**名额要归还**（并发位、连接、线程）。

### 4.3 成本控制（并发 1 之外）

- 用户级频率限制。
- 全局调用预算。
- 忙碌时的明确响应（不是静默排队）。
- **进程内计数重启即丢**，这一点必须写清，别把它当成分布式配额。

### 4.4 [待定] 数据外发清单

字段级白名单：可发给模型的字段、只留在后端的字段、错误日志的脱敏范围。S0 收口时定稿，见 §9。

## 5. [复核修正] 新鲜度校验口径

- 只比较**稳定业务字段和引用来源**；**查询时间窗口固定**。
- 不把查询时刻、耗时、动态超时状态放进指纹——它们每次都不同，会造成恒定误报。
- 首版：**关键证据变化 → 整份报告标未完成**；复杂的局部修补暂不实现。

## 6. 实施顺序（"做完"= 验收通过，不是类写齐）

| 阶段 | 实际操作 | 通过判据（做下一片的前提） |
| --- | --- | --- |
| **S0 固定契约** | 把本轮修正写进本文件；确定完成判据、终止协议、状态组合、预算计数、测试环境 | 契约能直接转成测试，且 §9 清单已关掉 |
| **S1 协议最小闭环** | 用虚构工具走通「模型请求工具 → 程序执行 → 回传结果 → 提交报告」；先用 HTTP 桩验证 | 正常、坏参数、超大响应、超时四类通过；再用虚构数据验真实供应商兼容性 |
| **S2 安全读取与基线** | 先实现一个受部门约束的真实工具和模板报告，再逐步加必要查询；同时建立确定性基线 | 跨部门、升级单、多角色测试全部通过，才接完整 agent 循环 |
| **S3 动态循环** | 加工具选择、证据登记、重复请求处理、统一预算、终止校验 | 能展示一条直接结束、一条依据结果扩查的轨迹 |
| **S4 接口与生命周期** | 接异步接口、前端状态、超时链、取消、限流和最终复核 | 断开、重启、权限撤销、业务状态变化都有明确结果，**不永久"调查中"** |
| **S5 回归与资源验证** | 隔离环境跑故障测试与既有分诊回归；查线程、连接池、内存与主业务影响 | 已定位问题解决后再冻结版本与评测集 |
| **S6 对照与收尾** | 比较三组方案，保留全部失败；整理复现材料、ADR、部署/关闭步骤 | 按实测决定默认方案，最后更新简历与面试材料 |

每个编码切片内部固定：**一个行为测试失败 → 最小实现通过 → 小范围重构 → 定向回归 → 检查 diff 与交付证据**。

命令口径：

- 先跑本片定向测试。
- 阶段收口跑 `mvn clean compile`；确认外部状态隔离后跑 `mvn test`。
- 改前端跑 `npm run build`；它只是编译构建检查，**不能当作交互测试通过**。
- 不自动跳过失败、不自动提交；记录实际命令、结果与未验证项。

## 7. [复核修正] 评测设计

- **三组对照**：纯规则报告 → 固定查询＋LLM → agent。三组跑同一批用例、同一套质量底线。
- **移除统一 20% 门槛**：先固定质量底线，再报告**逐案例收益、成本与失败**；根据实测决定业务默认方案。
- **查询成本**：用代表性数据对相关工单、日志分页、部门关联查询做执行计划核验（§2.1）。
- 失败样例全部保留，不缩分母（与 §2.3 第 2 项同源）。

## 8. AI 协作方式

两个 skill 就够：

- **`grill-with-docs`**：开工前、或出现真实业务冲突时，检查术语、边界与取舍。**已确认的八项直接复用，不重复采访**。
- **`tdd`**：每个实现切片一次一个公开行为，避免"一次生成全部测试再一次生成全部实现"。

`tdd` 在本项目的边界：**同事务、幂等、持久化不变量仍需要数据库证据或故障注入**；不能机械地把查库断言和内部故障注入都删掉。

提示词真正起作用的部分是：**限定范围、明确验收、要求真实证据**。
