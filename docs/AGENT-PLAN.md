## 2. [复核修正] 需要修正的七处

| # | 问题 | 上一版的不足 | 修正 |
| --- | --- | --- | --- |
| 1 | **agent 的价值可能被高估** | 报告被限制为事实编号和模板建议后，很多结果可以直接由规则产生 | 增加三组对照：**纯规则报告 → 固定查询＋LLM → agent**；避免只证明 agent 优于一个本来就不需要模型的方案（详见 §7） |

   > 它**没有进入 `RUNNING`**，因此**不在 §3.3 的状态组合里**（那是"运行的状态"，这是"没让它跑起来"）。

  > **另外两道拒绝（2026-10-07 补，D95）**：`RATE_LIMITED` → HTTP `429 TOO_MANY_REQUESTS`（这个用户请求太密）；
   > `BUDGET_EXHAUSTED` → HTTP `503 SERVICE_UNAVAILABLE`（进程内累计模型调用预算用尽）。
   > 与 `BUSY` **并列但不同码**：三种拒绝的**成因**不同（同时刻挤 / 单人太密 / 全局额度到顶），
   > 用户可采取的**动作**也不同（稍后重试 / 降频 / 找管理员）——复用同一个码会让调用方没法区分。

  > **顺带修的一处**（本轮用例逼出来的）：`GlobalExceptionHandler` 的 catch-all（`Exception.class`）原先把
  > "无匹配 handler"也吞成 **HTTP 200 + code=500**——"功能没开/路径写错"会被读成"服务器内部错误"。
  > 现在 `NoResourceFoundException` / `NoHandlerFoundException` 单独映射为 **404**（`Result.fail(NOT_FOUND)`）。

  **最终短读取复核（2026-10-06 落地，设计稿 L213）**：报告通过校验、**返回 `COMPLETED` 之前**，
  由**同一个协作者** `FinalReview` 重查一遍——agent 与基线**共用**（否则 S6 的对照不公平）。

  | 项 | 口径 |
  | --- | --- |
  | 重查什么 | 主单的关键业务字段：用**同一个工具**（`get_order_facts`）重跑一遍，把结果与证据里登记的 fact **逐字段比对**（渲染口径因此天然一致，不会出现"复核另用一套格式化"） |
  | 对照单 | 证据里引用的对照单单号（`dept.*_order_nos`）逐个重查：**提交人是否仍在调用者部门可见范围内**；不在 → 判变化 |
  | 不一致的终态 | `INCOMPLETE(STATE_CHANGED)`：`report == null`、**已核实事实保留在 `evidence`**、渲染走 `renderIncomplete(...)`（顶部"调查未完成（STATE_CHANGED）"，不出现【结论】与【下一步核实建议】） |
  | **version 不参与判定** | 设计稿："version 单独不够：`markTriageFailed` 不递增 version"。它是**并发控制字段**：变了不代表业务事实变了、不变也不代表没变。所以"只改 version"**不算变化**（有用例钉住） |
  | 不放进指纹 | 查询时刻、耗时、动态超时状态（§5：会造成恒定误报）；`order.logs_page` 这类**依赖游标的分页切片**（切片是相对量，口径要先定） |
  | 尚不能比对 | `type` / `priority` / `triageStatus`——设计稿列了它们，但**当前工具不产出这些事实键**，无从比对；**不假装比过**，一旦产物化必须一并纳入 |
  | 成本口径（**已知偏离**） | 设计稿 L213 说"复核 SQL/时间计入总成本"，当前**没有**计入 `toolCalls`（它不是模型请求的工具调用）。登记在 D90，另轮定计数口径 |

  **工具调用前的权限重校验（2026-10-06 落地，设计稿 L116 第 3 条）**：

  | 项 | 口径 |
  | --- | --- |
  | 检测点 | **每次工具调用之前**（含入口预读）；agent 与基线**共用同一个** `PermissionRecheck` 实例 |
  | 重校验什么 | 从**数据层**重新解析调用者的账号 / 角色 / 部门——用 `WorkOrderService.resolveDepartmentScope(userId)`（与列表接口、与受理层**同源**，D85），**不另写** `isAdmin()` 之类的本地判断 |
  | 判据 | 与 `ToolContext` 的**受理期快照**比对：已不是 `DEPT_ADMIN`/已无部门、部门与快照不一致、或部门载体不可解析 → 一律**撤销** |
  | 终态 | `CANCELLED(PERMISSION_REVOKED)`：`report == null`、**已核实事实保留**、渲染走 `renderCancelled(...)`（顶部"调查已取消（PERMISSION_REVOKED）"，与"未完成"同一形态但措辞不同） |
  | **不切换范围** | **终止即终止**：发现部门已变后**不得**按新部门继续查（L116 原话"主管调部门则终止，不切换到新范围"）。用例用计数桩钉住"撤权那一轮之后没有任何新查询" |
  | **会话校验在执行期不适用** | L116 说"重新校验**会话**、账号、权限、主管当前部门"，但执行线程（S4 的消费/调度线程）**没有 Sa-Token 会话**（§11-2 已定稿"执行侧不重新取值，那里没有会话"）。所以本轮**只重校验数据层**，**不伪造一个会话检查** |
  | 成本（D91） | 每次工具调用前多一次"账号/角色/部门"解析查询；**本轮不做缓存**——缓存会把"撤销后仍按旧范围跑"重新引进来，正是本条要防的事 |
  | 已知边界 | 检测点在**工具边界**：若撤销发生在**最后一次工具调用之后**，本轮检测不到（那需要 S4 的取消/状态机），登记在 D91 |
- **校验项（全部由后端做）**：① 每个 `evidenceId` / `suggestionId` 在本轮真实存在；
  ② §3.1 的必需事实全覆盖；③ `UNSUPPORTED` 时两个数组都为空。
- **终止动作必须单独一轮提交**：`finish_report` 与其它工具调用混在同一轮 → `FAILED(MODEL_PROTOCOL_ERROR)`。
  理由：混在一轮会允许"报告引用同一轮才产生、模型还没看到结果的证据编号"——那不是模型的判断，是协议的巧合。
- **校验失败的处理（本条已裁决）**：第 1 次不通过 → 把**缺口清单**（哪些编号不存在 / 哪些必需事实没被覆盖）
  作为系统消息回传，允许重交 1 次；第 2 次仍不通过 → 终态 `FAILED(REPORT_INVALID)`，**不产出报告**。
- **不可绕过**：终态为 `INCOMPLETE` / `FAILED` / `TIMED_OUT` / `CANCELLED` 的运行，`report` 必须为 `null`——
  这是"失败不得被伪装成正常报告"的机器判据，S1 用测试钉住。**`INCOMPLETE` 也走这条**（D86）：
  它有经复核的部分事实、但**没有完整报告**，已核实事实只走 `evidence`，不新增"部分报告"这种第二形态。

### 3.3 [已定稿 2026-10-05] 对外状态组合

| 状态 | 进入条件 | 终态 | 对外呈现 |
| --- | --- | --- | --- |
| `RUNNING` | 已受理、未出终态 | 否 | 调查中 |
| `COMPLETED` | 报告通过 §3.2 全部校验 | 是 | 报告（`problemType` 可能是 `UNSUPPORTED`） |
| `INCOMPLETE` | 有经复核的**部分事实**、但没有完整报告（超时 / 预算 / 工具失败 / 状态变化等阻止完成） | 是 | **调查未完成** + 原因码，**无报告**；已核实事实走 `evidence` |
| `FAILED` | 命中下表的失败原因码 | 是 | 失败 + 原因码，**无报告** |
| `CANCELLED` | 用户主动取消；或运行中权限被撤销 | 是 | 已取消 + 原因码 |
| `TIMED_OUT` | 运行预算 60s 到（§4.1）；或模型读取超时 | 是 | 超时 + 原因码，**无报告** |

失败 / 终止原因码（首版可用集合；**不是闭集**——新增码必须同步本节与 §5.1 矩阵，见 `docs/DECISIONS.md` D86）：

| 原因码 | 含义 |
| --- | --- |
| `RUN_BUDGET_EXCEEDED` | 运行时间超过 60s |
| `TOOL_BUDGET_EXCEEDED` | 工具调用次数超过上限（§3.4） |
| `ROUND_LIMIT_EXCEEDED` | 模型轮次超过上限（§3.4） |
| `RESPONSE_TOO_LARGE` | 模型响应超过读取上限（§4.2） |
| `MODEL_TIMEOUT` | 模型连接 / 读取超时 |
| `MODEL_UNREACHABLE` | 模型不可达 |
| `MODEL_HTTP_ERROR` | 模型返回非 2xx |
| `MODEL_PROTOCOL_ERROR` | 响应可读但不是合法协议（既无工具调用也无终止动作 / JSON 非法） |
| `NO_PROGRESS` | **连续两轮没有产生任何新证据**（重复调用命中本轮快照缓存、调查没有推进）——D84 裁决"两轮"为终止门槛 |
| `REPORT_INVALID` | 报告两次校验均不通过（§3.2） |
| `FORBIDDEN` | 调用者不在数据范围内（受理层非部门主管拒绝；两个工具的跨部门拒绝）——D85 / D86 |
| `STATE_CHANGED` | 运行中关键证据 / 业务状态变化（`triageStatus` / `deadline` 等）→ 终态标为"未完成"，只交付经复核的部分事实（§5.1 槽24；D86） |
| `STALE_EVIDENCE` | **旧名，已被上一行的新名取代**（对外口径以 §5.1 矩阵槽24 为准）；保留此行仅为历史可查 |
| `PERMISSION_REVOKED` | 运行中权限被撤销 |
| `USER_CANCELLED` | 用户主动取消 |

> 收口时删掉了原先拟的 `NOT_SUPPORTED`：**"不属于支持范围"由 `COMPLETED` + `problemType=UNSUPPORTED` 表达**
> （它是结论，不是故障）；而"模型交出一个不在列表里的类型"属报告非法，走 `REPORT_INVALID`。
> 留一个永远不会产生的状态码，只会让下一个人以为它需要被实现（回读校验时发现，遂删）。

**运行之外的拒绝码**（2026-10-07 补：它们**没有进入 `RUNNING`**，所以不占上面那张表的名额；
但**必须登记**，否则"产生了却查不到"——这正是当初删 `NOT_SUPPORTED` 的反面教训）：

| 拒绝码 | 含义 | HTTP 层 |
| --- | --- | --- |
| `AGENT_BUSY` | 并发名额已满（同时刻挤）——D93 | `409 CONFLICT` |
| `RATE_LIMITED` | 该用户在窗口内的调查次数已达上限（单人太密）——D95 | `429 TOO_MANY_REQUESTS` |
| `BUDGET_EXHAUSTED` | 进程内累计模型调用预算用尽（全局额度到顶）——D95 | `503 SERVICE_UNAVAILABLE` |

三者的**成因与用户可采取的动作都不同**，所以**不复用同一个码**。

**"永久调查中"的反面**：任何进入 `RUNNING` 的运行都必须同时挂在**三个有上限的口径**上——运行时间（60s）、
工具调用次数（12）、模型轮次（8）。三者任一触顶都进终态，**没有任何路径会停在 `RUNNING`**。

**权限撤销与业务状态变化的终态**：权限撤销 → `CANCELLED(PERMISSION_REVOKED)`；
业务状态变化导致关键证据变化 → `INCOMPLETE(STATE_CHANGED)`（只交付经复核的部分事实并标未完成，不做局部修补，见 §5）。

**S2 的承诺边界（2026-10-06 定稿，D79）**：`ToolContext` 是**受理时的一次性快照**（§11-2），
所以"受理之后"发生的调岗 / 撤权**在执行期间不会被感知**——S2 **只承诺"受理时正确"，不承诺"执行期间实时"**；
"执行期间权限变化"由本条的 `PERMISSION_REVOKED`（S4）覆盖，S1/S2 都不得声称已覆盖它。

⚠ **S1 落地状态**：`PERMISSION_REVOKED` 与 `STATE_CHANGED` 在 S1 **只登记不落地**——S1 没有权限来源、也没有业务表，无法产生这两类事件；
它们在 S4 由"断开 / 重启 / 权限撤销 / 业务状态变化"四个用例断言。
**更正（2026-10-06）**：`STATE_CHANGED` **已经有生产者**了——最终短读取复核（§3.2）在返回 `COMPLETED` 前逐字段重查，
不一致即 `INCOMPLETE(STATE_CHANGED)`（用例 `FinalReviewTest`，5 条）。
**`PERMISSION_REVOKED` 也已经有生产者**：每次工具调用前的权限重校验（§3.2）发现调用者被撤权/调部门 →
`CANCELLED(PERMISSION_REVOKED)` 并**终止**（用例 `PermissionRecheckTest`，4 条）。
**边界**：检测点在工具边界——撤销发生在**最后一次工具调用之后**时检测不到（登记 D91），仍属 S4 的取消/状态机范围。
S1 的测试只覆盖 `RUNNING → COMPLETED / FAILED / TIMED_OUT` 这条主干，**不得声称已覆盖权限与业务状态变化**。

### 3.4 [已定稿 2026-10-05 · **参数待实测** 2026-10-06] 预算计数

| 口径 | 计数对象 | 上限 | 超限终态 |
| --- | --- | --- | --- |
| 时间 | 运行墙钟 | 60s（§4.1） | `TIMED_OUT(RUN_BUDGET_EXCEEDED)` |
| 工具 | **工具调用次数**（含非法工具、坏参数这类"调了但失败"的） | 12 / 次调查 | `FAILED(TOOL_BUDGET_EXCEEDED)` |
| 轮次 | 模型往返轮次（防"只说话不调工具"空转） | 8 / 次调查 | `FAILED(ROUND_LIMIT_EXCEEDED)` |
| 终止 | `finish_report` 提交次数 | 2（首次 + 重试一次，§3.2） | `FAILED(REPORT_INVALID)` |
| token | **不计** | — | — |

- **为什么 token 不计**：首版拿不到跨供应商一致的 `usage` 字段（有的不返回、有的只返回总量），
  拿不到的字段当上限会变成"看起来有配额、实际恒不触发"的假保护。代价写明：**首版没有 token 级成本闸门**，
  只能靠调用次数与轮次间接限制。
- **计数是进程内计数，重启即丢**（§4.3）：它不是分布式配额、也不落库；跨进程配额由 S4 的频率限制承担，S1 不做。
- **运行中有界重试（2026-10-07 落地，D92）**：**在模型边界**（`HttpAgentModel`）重试，**不在循环里再包一层**
  （那会重复计数）。四个界：
  · **只重试可恢复类**：HTTP **429**、**5xx**、连接类（`MODEL_UNREACHABLE`）；
    **非 429 的 4xx 一律不重试**（400/401 这类重试多少次都一样——槽 22 的"无谓重试"）。
  · **次数上限 3 次物理调用**（含首次）；**单次等待上限 2s**（`Retry-After` 只是参考值，不得超过它）；
  · **总等待受本轮剩余预算约束**：睡下去会超出预算就不睡，直接按 `MODEL_TIMEOUT` → 循环翻成
    `TIMED_OUT(RUN_BUDGET_EXCEEDED)`；
  · **物理调用次数回传**：失败消息里带"已重试 N 次 / 物理调用 N 次"，`AgentModelException.attempts()` 可读——
    重试**不能藏起来**。重试用尽**复用 `MODEL_HTTP_ERROR`**（不新开码）。
  · 耗时口径：重试与等待都花在这一轮的读超时里，而那一轮又受运行预算收敛 → **墙钟自然计入**，不需要新字段。
- 非法工具与坏参数**照常计入**工具预算——否则"报错重试"就成了绕过预算的免费通道。
 - **命中本轮快照缓存的重复调用同样计入**（设计稿 L133 的"仍计工具请求"）——否则重复调用成了另一条免费通道；缓存只复用结果，不减预算。
- **参数状态：待实测（2026-10-06 C3 裁决，§1.1）**。上表这组值（工具 12 / 轮次 8 / 墙钟 60s / 响应体 256 KiB）
  是**当前实现与测试里唯一有证据的一组**（`AgentLimits.s1Defaults`，由 38 条 agent 用例覆盖），
  因此**作为初值生效**；但它**不是实测校准过的值**，一律标"待实测"。
  - `AGENT-DESIGN.md` §4 另给过更紧的一组（动态工具 ≤4 次、模型响应 64 KiB、工具结果 16 KiB、模型输入 48 KiB），
    登记为**待验证候选**——**不因为数值更小就采纳**：收紧前必须先证明**合法调查路径仍能跑完**。
  - 收口方式：S2/S3 用真实工具做一次实测（含边界用例），再决定是否收紧或放宽，结果登记 D 条目。

### 4.2 读取阶段的限流与释放

- 限字节必须落在**读取循环里**（读满即中止并释放连接），不能在读完整响应之后再判大小。
- 取消要验到**底层资源真的释放**：用慢响应、超大响应、连接不结束三种桩。
- 取消后**名额要归还**（并发位、连接、线程）。

**S1 已落地的部分与初值**：模型响应体上限 **256KB**（`AgentLimits.maxModelResponseBytes`，在
`HttpAgentModel.readAtMost` 的读取循环里判定），超过即 `FAILED(RESPONSE_TOO_LARGE)`；
"取消要验到资源释放"与"名额归还"属 S4 的异步接口范围，S1 **未落地**。

**取消延迟上界 = 当前轮读超时（2026-10-06 裁决）**：阻塞 `read` **不响应 `interrupt`**，
所以"取消"只会在当前轮的读超时返回之后才生效——**不能把 `Future.cancel(true)` 当成"资源已释放"**。
该上界已被剩余预算收敛（见 §4.1），要缩短只能换可中断 IO，属 S4 选型；S4 验收必须包含
"连接真的断开 + 名额真的归还"的实证，见 §11-3。

> **已落地（2026-10-07，D94）**：`Cancellation`（取消信号）+ `AgentModel.respond(..., Cancellation)`
> + `HttpAgentModel` 的**读取循环里检查标志**（每个 chunk 一次）并在取消时**主动 `disconnect()`**。
> 调查循环**每轮开始前**也检查一次（取消之后不再发下一个请求）。终态 `CANCELLED(USER_CANCELLED)`：
> `report == null`、已核实事实保留；**名额由同一个 `Permit.releaseOnce()` 归还**（D93）。
> **有意不用 `Thread.interrupt()`**：这条链路上的等待点是阻塞 `read`，它不响应 interrupt——
> 用它只会得到"标志置上了、请求还在跑"的假象；**上界仍是当前轮读超时**（要用 interrupt 真缩短它，
> 得先把客户端换成可中断 IO，属后续选型）。

> **同步更新（2026-10-06 实测校准后）**：§4.1 把 agent 侧单轮读超时从 30s 提到 **45s**，
> 所以"取消延迟上界"也跟着从"≤30s"变成"**≤45s**（且不超过本轮剩余预算）"——
> 这是**取舍的代价**：单次调用更不容易被误杀，代价是用户点取消后最坏要多等 15s。
> 要同时缩短两者只能换可中断 IO（S4 选型）。

### 4.3 成本控制（并发 1 之外）

- 用户级频率限制。
- 全局调用预算。
- 忙碌时的明确响应（不是静默排队）。
- **进程内计数重启即丢**，这一点必须写清，别把它当成分布式配额。

**有界并发位 + 忙碌响应 + 名额归还（2026-10-07 落地，D93；槽 23 的前半）**：

| 项 | 口径 |
| --- | --- |
| 名额 | 受理层 `AgentInvestigationService` 持一个 `Semaphore`；容量可配（`agent.investigation.max-concurrent`，**默认 1**——本节标题就是"并发 1 之外"） |
| 取不到名额 | **立即**返回 `BUSY / AGENT_BUSY`（HTTP 层 `409 CONFLICT`）：**不排队、不阻塞**（"忙碌时的明确响应，不是静默排队"）。它**没有进入 RUNNING**，所以不在 §3.3 的状态组合里 |
| 归还时机 | **每一条终止路径**（COMPLETED / FAILED / TIMED_OUT / CANCELLED / INCOMPLETE，以及抛异常）都在 `finally` 里归还——归还发生在**执行体返回之后**（底层资源已释放） |
| 归还幂等 | `Semaphore.release()` **多调一次就多一个名额**，所以由句柄 `Permit` 记"已归还"、**只 release 一次**（D93） |
| 忙碌的代价 | 被拒绝的那次**不消耗模型调用、不产出报告**（有用例用桩计数证明） |
| 重启即丢 | 名额是**进程内**的：重启归零、多实例各自独立（与上面的"进程内计数"同性质） |

> **仍未落地的"真正取消"**（S4，D93 登记）：本轮解决的是**名额不泄漏**；
> **打断进行中的调查**（interrupt / 连接断开 / 读循环中止）还没做——它卡在
> **IO 不响应 interrupt** 这个物理事实上（阻塞 `read` 只会在读超时返回后才看到中断，见 §11-3），
> 所以"取消延迟上界 = 当前轮读超时"。衔接方式：将来的取消路径**也要走同一个 `Permit.releaseOnce()`**，
> 而不是自己再写一套归还。

**两道限流闸门（2026-10-07 落地，D95）**：与**并发位**三者**正交**，别混为一谈——

| 闸门 | 管什么 | 取值（初值） | 超限的对外码 |
| --- | --- | --- | --- |
| **并发位**（D93） | **同时刻**最多几个在跑 | `agent.investigation.max-concurrent`，默认 **1** | `BUSY / AGENT_BUSY`（HTTP 409） |
| **用户级频率限制** | **单位时间内每人几次** | `agent.investigation.rate.window-seconds` 默认 **60s**；`rate.max-per-user` 默认 **3** | `RATE_LIMITED`（HTTP 429） |
| **全局调用预算** | **累计总量**上限 | `agent.investigation.global-model-call-budget` 默认 **1000** 次**模型调用** | `BUDGET_EXHAUSTED`（HTTP 503） |

- **三者相乘**：容量 1 + 每人每分钟 3 次 + 全局 1000 次 = "节奏受频率、并发受容量、总量受预算"。
  任何一道先触发就拒绝，**不排队**（"忙碌时的明确响应"）。
- **判断时点**：频率与预算都在**发起任何模型调用之前**判断（**不能扣在事后**）；
  放行时**立即记账**（否则并发进来的两个请求会读到同一个旧计数）。
- **全局预算按"次数"而不是 token**：与 §3.4 的理由一致——拿不到跨供应商一致的 `usage`，
  用它当上限会变成"看起来有配额、实际恒不触发"的假保护。首版取**逻辑轮次**当模型调用次数的代理
  （重试的物理次数当前不可见，见 D92 的登记）。
- **计数载体是进程内**：重启即丢、多实例各自独立（§4.3 明写"不是分布式配额"）——它是**成本护栏**，不是计费依据。
- **为什么 S6 开跑前必须先有这两道闸门**：holdout 的拟定规模是 24 槽 × 2 方案 × 3 次 = **144 次真实调查**，
  每一次都要真金白银；没有频率与总量闸门，一次脚本写错（循环跑飞、重试叠加）就能把预算烧穿。

### 11-2 工具调用上下文 —— 采纳方向，**形状与授权口径已定稿**，S2 第一片实施

- **裁决**：采纳方向。形状原为"只定形状"，**2026-10-06 补定为**：
  - **签名**：`AgentTool.execute(ToolContext ctx, JsonNode arguments)`；`ctx` 由调查循环构造并传入。
  - **`ToolContext` 的字段（三个，刻意压到最少；2026-10-06 C2 裁决由四个删为三个）**：
    - `investigationId` —— 本次调查的 id（日志与审计的串联键，**不是**用户身份）；
    - `callerUserId` —— 发起调查的用户 id（**唯一**的用户身份来源）；
    - `callerDeptId` —— 发起人所属部门 id；**它是唯一的范围载体**——§1 第二题裁定"统一只查本部门，
      升级状态不扩大可见范围"，因此**不接受任何"可跨部门"标志**（原 `canSeeAllDepts` 字段已删除）。
  - **工具的硬性约束**：`AgentTool` 实现**不得**读 Sa-Token（`StpUtil`）、**不得**依赖
    `RequestContextHolder`、不得读取任何"当前请求"的隐式状态；需要身份就**只用 `ctx` 里的字段**。
  - **授权口径（2026-10-06 定稿，`docs/DECISIONS.md` **D79**）**：
    - **取值时点**：`ToolContext` 在**受理调查的 Web 请求**里**一次性快照、之后不可变**；
      执行侧（S4 的消费 / 调度线程）**不重新取值**——理由同上，那里没有会话，想取也取不到。
    - **判定方**：`callerDeptId` 由**受理层**用与业务接口**同一套**权限判定得出
      （与列表接口的部门过滤同源）；agent 侧**不得**另写 `isAdmin()` / "可见全部" 之类的本地判断
      ——两套判定迟早漂移，而漂移的方向总是"一边放宽"。
    - **拒绝方式**：用**构造期不变量**（`IllegalArgumentException`），**不新开失败码**——
      `ToolContext` 的紧凑构造器拒绝 `null` / 空白 / 缺部门（标识字段首版按**不透明字符串**处理；
      类型属实现细节，S2 可定，但不变量不得放宽）。**造不出对象，就没有"跑到一半才发现越权"的路径。**
    - **硬约束**：**`callerDeptId` 必须非空**（构造期拒绝 `null` / 空白）。§1 之后没有"跨部门"这个口子，
      所以"缺部门"就等价于"没有过滤条件"（= 越权）——**不存在的状态不该能构造出来**。
    - **承诺边界**：S2 **只承诺"受理时正确"，不承诺"执行期间实时"**——快照会过时
      （受理后调岗 / 撤权，本次调查仍按旧权限跑完），这正是 §3.3 的 `PERMISSION_REVOKED`（S4）覆盖的场景。
    - **S2 实施时不得放宽本口径**：放宽 = 改契约，要走 D 条目。
    - **准入条件（2026-10-06 越权修复轮补，`docs/DECISIONS.md` **D85**）**：**不是"有部门"就能拿到部门范围**——
      准入 = `DEPT_ADMIN` 且部门非空 → `DEPARTMENT(deptId)`，其它角色（含 `SYS_ADMIN`）→ `NONE`，
      受理层对 `NONE` 回 `FAILED / FORBIDDEN`（不产出报告与文本）。
      **准入**与"取哪个部门"合并为**一个**共享判定 `WorkOrderService.resolveDepartmentScope(userId)`，
      由 `applyRoleFilters` 与受理层**共同调用**；此前只共用了解析函数 `callerDeptId`、没共用准入，
      于是**任何有部门的普通用户**都能让助手读到全部门工单（列表接口里同一用户只能看到自己）——
      这正是 D79 警告的"漂移方向总是放宽"。
      **`SYS_ADMIN` 是否可用登记为待裁决**（§1 第一题只写"面向部门主管"），本轮**不放行**；放行须走 D 条目。
- **排期**：S2 第一片（与第一个真实工具一起改签名）。
- **理由（比"越权风险"更硬的一条）**：S4 的调查跑在**消费 / 调度线程**上，那个线程**没有 Sa-Token 会话**——
  工具若自己去读登录态，不是"可能越权"而是**根本跑不起来**；`RequestContextHolder` 同理（那里没有请求上下文）。
  所以"调用者身份显式传入"不是防御性设计，而是**可行性前提**。
- **代价**：所有工具实现都要改签名（S1 只有 2 个虚构工具，现在是最便宜的时点）；
  `ToolContext` 一旦定下就是**跨片协议**，加字段要走 D 条目——四个字段压到最少正是为此：
  加 `requestId` / `tenantId` 这类"以后可能有用"的字段，就是要避免的过度设计。

### 11-3 取消 —— 采纳，**S4 实施**

- **裁决**：§4.2 补一条**取消延迟上界 = 当前轮读超时**（阻塞 `read` 不响应 `interrupt`，
  所以"取消"只会在读超时返回后才生效）。
- **排期**：S4；验收必须含**连接断开 + 名额归还**的实证（不是"调用过 cancel"）。
- **代价**：用户点了取消之后，最坏仍要等一个读超时（该值已被剩余预算收敛，见 §4.1）；
  要缩短只能把客户端换成可中断 IO，属 S4 的选型。

> **落地状态（2026-10-07，D94）**：已实现——`Cancellation` 信号 → 模型读取循环**每个 chunk 检查一次**、

> **验收实证**：`CancellationTest`（4 条）——置位后不再发下一个请求 / 取消期间不泄漏名额（下一个能进）/
> 终态与 `report == null` / **取消延迟 < 当前轮读超时**（用流式响应量出上界）。

### 11-4 建议前提分级 —— 采纳，**只做禁止项、不做强制项**

- **裁决边界**：
  - **禁止项（要做）**：`order.assignee` 未知（未分配）时 `suggestionIds` 不得含 `CONTACT_ASSIGNEE`；
    `order.accept_events` 为空时同理不得含 `CONTACT_ASSIGNEE`。
    **2026-10-07 追加第三条（同一档，不改上面的裁决）**：`order.status` 不是 `AWAIT_APPROVAL` 时
    `suggestionIds` 不得含 `WAIT_FOR_SUBMITTER_ACCEPTANCE`——"下一步在提交人侧"的唯一依据是状态机，
    与"不知道找谁却建议联系某人"同一形状；落地见 `AgentReportValidator.checkProhibitedSuggestions`（D106）。
  - **不做强制项**：不实现"必须建议 X"——那会把建议变成填空题。
  - **无原因结论（C1 裁决）**：`TIMEOUT_SITUATION` **不得输出原因性结论**——只交付已核实事实、
    证据缺口与核实建议。约束落在**输出与完成判据**上，名字本身证明不了行为违规。
  - **过期判定（要做）**：`TIMEOUT_SITUATION` 的"`sla_deadline` 是否已过期"必须实现，但**必须用可注入的 `Clock`**，
    不许内联 `Instant.now()`（否则测试不可控、时间源不可替）。
  - **按数据能力对齐的两处（D82，2026-10-06）**：① `order.alert_count` **移出** `TIMEOUT_SITUATION` 的必需事实、
    **保留在允许未知**（映射表已证"无列、只能近似"，不配当必需；若同时从允许未知里删掉，工具返回的显式未知
    一旦被引用就会撞 validateReport 的"该类型不允许未知"分支）；② 证据能证明 `order.exists=false` 时，
    必需事实**收缩为 `{order.exists}`**——"工单不存在"本身就是可完成的结论。两处只改判据口径，不动 §3.1 的其它列。
- **排期**：随 S2 的真实工具（有真实 SLA 数据）落地；S1 保持"仅提示"，§3.1 已标注。
- **代价**：禁止项会拦掉"未分配但确实该联系某人"的场景——首版接受，因为**编造处理人**的代价更高；
  引入 `Clock` 会多一个注入点，S2 要明确它的时区口径（与 §4.1 同源的问题）。
- **失败码**：**复用 `REPORT_INVALID`**，不新开——口径是"报告不合法就是报告不合法"，与"缺事实"同类。

### B.3 一条成功轨迹与一条失败轨迹

**成功**（`toolCallThenFinishReport_completes`）：模型请求 `stub_order_snapshot` → 程序执行 →
回传 `{"ok":true,"facts":{...},"evidenceIds":{"order.status":"E2",...}}` →

缺口回传 → 模型重交同样内容 → `FAILED(REPORT_INVALID)` 且 `report == null`。
**没有退化成"编一个从未接单的结论"**。

### B.4 为什么失败不会被伪装成正常报告

两条都是机器判据，不靠约定：

1. **构造期不变量**：`AgentRunResult` 的构造器强制"非 `COMPLETED` ⇒ `report == null` 且必须带原因码"。

2. **完成判据落在证据上**：由 §3.1 的必需事实覆盖度判定，不看模型表述；用例
   `modelNarrativeWithoutEvidence_doesNotCount` 专门喂"报告里写结论、一个证据都不引"的输入，验证它仍然失败。
