## 已确认的选择

1. 新增独立能力，不改变现有 AI 分诊链路。
2. 用户选择方向 A：面向部门主管的只读工单调查助手。
3. 本轮只做设计，不修改项目代码，不提交。
4. 学习目标包含工具调用、多步循环、护栏和评测；最终设计要说明为什么此任务需要 agent，以及是否采用框架的取舍。
5. 第二题用户选择 A：助手统一只调查本部门用户提交的工单，`ESCALATED_ADMIN` 升级状态不扩大可见范围。
6. 第三题用户选择 A：以指定工单为起点，允许按需查询同部门其他工单作为对照；证据足够即可停止，不要求每次扩查。
7. 第四题用户选择 A：第一版交付可核验事实、证据缺口及下一步核实建议，不生成未经证实的原因假设；允许明确回答“现有记录无法确定延误原因”并正常完成调查。
8. 第五题用户选择 A：第一版采用单次调查报告；一次请求内允许多步模型与工具交互，后续提问发起新调查，不自动继承上一轮对话记忆。
9. 第六题用户选择 A：进程中断后不自动接续调查，用户能够识别未完成并重新发起；运行期间的有限重试仍可单独设计。
10. 第七题用户选择 A：首版手写仅服务于本模块的最小执行循环，不引入 agent 编排框架，不开发通用 agent 平台。
11. 第八题用户选择 A：固定流程公平对照列为必须验收；没有证明 agent 的净收益时，保留学习实现与实验结果，不宣称业务方案更优。

## 已确认：调查的数据范围

只调查本部门用户提交的工单，升级状态不扩大范围。

未选择：普通工单限本部门、升级单跨部门开放。代价：本助手不能帮助主管调查跨部门升级单；这是新模块范围的裁决，不代表已经裁决或修改原详情接口的规则。

这里的“本部门”依据现有列表实现，指提交人当前所属部门与主管当前所属部门相同；不是处理人所属部门，也不是独立的工单归属部门字段。

用户部门变化、多角色叠加、调查期间权限变化的具体执行语义尚待设计；不能借上述情况静默扩大已确认的调查范围。

## 已确认：允许按需调查同部门其他工单

第三题用户选择 A：以指定工单为起点，必要时查询同部门其他工单作为对照证据，例如当前处理人在本部门可见范围内的其他未结工单；证据足够即可停止，不要求每次扩查。

未选择：始终只读指定工单自身的详情、日志与适用规则。即使允许扩查，也仍需与“固定查询后一次总结”比较，不能仅因调用多次模型就宣称 agent 更有价值。

不能把“可见工单多”写成“处理人总负荷高”，更不能直接断言它就是本单延误的原因；其他部门工单仍不可查询。工具集合、每次查询的条数与时间范围、循环预算均未定稿。

## 已确认：证据不足时交付事实与核实建议

第四题用户选择 A：以可核验的事实和下一步核实建议为完成标准，允许明确回答“现有记录无法确定延误原因”。不把检索已完成包装成原因已查明。

未选择：额外生成按证据排序的原因假设。第一版不承担对这种假设排序与合理性进行评测的责任，也不虚构原因概率或置信度。

用于讨论的假设场景（非项目实测数据）：某单两天没有新的处理日志，同一处理人在本部门还有 12 张未结工单，但没有记录延误原因。上述记录不能直接证明“人手不足导致延误”；没有新日志也不能证明线下没有工作。

正常完成检索但证据不足，与工具失败、权限拒绝、预算耗尽必须区分，不能把这些情况都呈现为“没查到”。具体运行状态和评测判据待后续设计。

## 已确认：单次调查报告

第五题用户选择 A：一次用户请求对应一次独立调查；调查内部可以多次调用模型、执行工具并根据结果决定后续步骤，最终返回一份报告。用户下一次提问发起新的调查，重新鉴权、读取需要的事实，不自动继承上一轮对话记忆；缺少线下事实时在报告中给出核实建议，不挂起等待补充后自动续跑。

未选择：支持连续追问与补充、在后续消息中继承同一会话上下文。代价：用户不能依靠“刚才那张单”等上轮指代继续对话，需要在新调查中明确对象与问题；换来第一版不承担跨轮会话记忆的维护。

此处仅选择交互范围，不提前决定同步 HTTP、异步任务、流式输出或持久化方案；单次调查也不等于不保留审计轨迹。

## 已确认：进程中断后不自动续跑

第六题用户选择 A：调查途中后端重启或进程崩溃，不自动接续上一次调查；用户能够识别该次调查未完成，并可重新发起。新调查重新鉴权并读取当前数据，不把上次未完成的结果当成已完成报告。

未选择：服务恢复后自动接续尚未完成的调查。接受的代价是用户需要重新发起，部分查询与模型调用会重复，已消耗的 token 不会退回；换来第一版不承担跨进程恢复执行进度的承诺。

本题的“恢复”仅指进程中断后的自动接续；正常运行期间，对可重试的模型或工具失败做有次数与时间上限的重试，是另一项执行策略，尚待设计。选 A 不意味着所有失败都不重试，也不意味着调查必须使用同步 HTTP。

界面不能永久停留在“调查中”；如果最终设计持久化运行状态，就必须给出进程中断后的状态收口方案。是否新增数据库表与如何保存轨迹仍未决定。

## 已确认：首版手写最小执行循环

第七题用户选择 A：先手写只服务于本模块的最小执行循环，沿用 Java 后端已有的 HTTP 与 JSON 能力，明确实现模型请求、工具调用解析、白名单与参数校验、权限校验、工具执行、结果回传和停止条件。首版不引入 agent 编排框架，不开发通用插件系统、流程 DSL 或多 agent 平台；这里的“手写”不是手写 HTTP/JSON 基础库。

未选择：首版采用现有框架的模型与工具抽象。框架可以承担部分工具调用与消息管理代码，未来仍可重新评估引入；部门权限、执行预算、状态与评测契约始终需要按本项目定义。

推荐 A 的依据是已经确认的范围：单个助手、只读工具、单次调查、无跨轮记忆、无崩溃后接续，且学习目标明确包含理解循环本身。接受的代价是要自行维护工具协议处理、调用与结果关联、错误分流等代码与测试；不能把手写宣称为天然更可靠、更快或更省资源。

未来若引入框架，必须另行核对与现有 Spring Boot 3.3.5 / Java 17 的依赖兼容性；本轮不选择框架或版本，也未做兼容性实测。后续若演进到多供应商或更复杂编排，应重新比较维护成本，不以“从来不用框架”作为原则。

### 本题的代码与外部依据

## 已确认：固定流程对照列为必做验收

第八题用户选择 A：同一组任务必须比较固定流程与 agent 的正确性、证据覆盖、权限与边界遵守、调用次数、token 和耗时。若 agent 没有可证明的净收益，仍保留学习实现与实验结果，但不把它宣称为更优的业务方案；业务默认路径的取舍依据结果决定。

未选择：把固定流程价值对照移出第一版验收。学习目标和正确性、安全边界验收继续保留。

这项选择不取消新增 agent 的学习目标，也不预先要求它在所有任务上胜出；要验证的是适用边界以及收益是否值得增加的调用与维护成本。

### 对照实验约束

- 固定流程基线必须足够强：允许按代码规则读取当前工单、时间线及有必要的同部门对照记录，再交给模型生成同样格式的报告；不能故意剥夺其已有数据访问能力。
- agent 使用相同的权限范围、数据快照、模型版本、任务集合与共同的最高预算，仅把下一步查询选择交给模型。记录实际资源使用，而不要求两边强行消耗同样多的调用。
- 调整提示词使用的样本与最终验证样本分开；期望结果预先规定允许引用的事实、必须说明的未知项与禁止的越权行为，不只看回答是否流畅。
- 超时、工具失败和预算耗尽保留在完成率分母中，并分别归因；不得复用旧分诊的 14/14 成绩作为本模块能力证明。
- 任何简历提升数字都必须来自实际运行记录；本轮只设计，不运行真实模型评测，不编造胜率、时延、token 降幅或节省工时。

### 已定位：评测清理 SQL 的正则分隔符

`scripts/triage-eval.py:227–229` 复用逗号连接的 ID 字符串生成正则，得到 `(949,950)`，而按事件 ID 逐个匹配需要表示备选项的分隔方式。本地字符串检查：`order:949:v0:ORDER_TRIAGE` 不匹配 `^order:(949,950):`，匹配 `^order:(949|950):`。

此检查未连接 MySQL、未执行删除。D68 附录也保留了逗号形式的 SQL；其“按打印 SQL 清理六表”的描述与脚本生成逻辑存在冲突，需要复核实际执行记录，不能据此推断服务器当前存在残留。

### 已定位：信息不足组在提交失败时缩小分母

`scripts/triage-eval.py:145–153` 的提交失败分支只为非信息不足组增加分母，信息不足组直接跳过，未增加 `insufficient_n`，与“失败不缩分母”的口径不符。

### 已定位：日志读取缺少归属校验

见上方代码事实；这是原文档已登记的缺口，不宣称是本轮首次发现。新模块的工具边界必须明确处理，不能仅依赖提示词约束。

### 数据能力边界：完成流转不等于有维修知识

现有提交验收链路没有采集维修过程或解决方案。它足以支持流程进展调查，但不能直接支撑“检索历史成功修复方案”的承诺。这是功能范围与可用证据的限制，不直接归类为现有系统缺陷。
